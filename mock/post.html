Rewriting our operator in 400 lines of Go

We had a six-thousand-line operator that nobody dared to touch. This is what we deleted, what we kept, and what the reconcile loop looks like now.

Published 26 Jul 2026 Updated 29 Jul 2026 4,900 words 22 min read

There is a moment in every platform team's life when the tool you adopted to save time becomes the thing you spend all your time on. Ours arrived on a Tuesday, in the form of a stack trace forty frames deep, none of them ours.

The operator had been generated three years earlier from a project scaffold. It had a controller, a webhook, four API versions, a conversion layer between them, and roughly six thousand lines of code — of which, we eventually measured, about four hundred did anything specific to our system. The rest was ceremony.

What the operator actually had to do

Before deleting anything, we wrote down the job in plain sentences. It turned out to be three: watch a custom resource, make a StatefulSet and a Service match it, and report readiness back onto the resource's status. That's it. Everything else was infrastructure for expressing those three sentences.

  • Watch ShardGroup resources across all namespaces.
  • Ensure the owned objects exist and match the spec, creating or patching as needed.
  • Write back a status the rest of the platform can wait on.
!

If you can't write your controller's job as three sentences, the problem isn't the framework. Go find the fourth sentence first — it's usually where the bugs live.

The parts we deleted

Two API versions had no live objects. The conversion webhook existed only to translate between them, so it went too — along with the certificate rotation job that kept it alive, and the two alerts that fired when that job failed.

The reconcile loop, in full

Here is the entire core of the new operator. It reads top to bottom, it has no hidden control flow, and every error path either retries with backoff or gives up loudly.

reconcile.go go · 34 lines 
// Reconcile brings the cluster in line with one ShardGroup.
func (r *Reconciler) Reconcile(ctx context.Context, req Request) (Result, error) {
    var sg v1.ShardGroup
    if err := r.Get(ctx, req.NamespacedName, &sg); err != nil {
        return Result{}, client.IgnoreNotFound(err)
    }

    if !sg.DeletionTimestamp.IsZero() {
        return Result{}, r.drain(ctx, &sg)
    }

    desired := buildStatefulSet(&sg)
    if err := r.apply(ctx, desired); err != nil {
        return Result{}, fmt.Errorf("apply statefulset: %w", err)
    }

    ready, err := r.countReady(ctx, &sg)
    if err != nil {
        return Result{}, err
    }

    sg.Status.ReadyShards = ready
    sg.Status.Phase = phaseFor(ready, *sg.Spec.Shards)
    if err := r.Status().Update(ctx, &sg); err != nil {
        return Result{}, err
    }

    if ready < *sg.Spec.Shards {
        return Result{RequeueAfter: 10 * time.Second}, nil
    }
    return Result{}, nil
}

The interesting decision is the last one. Instead of subscribing to pod events and maintaining a cache of readiness, we requeue every ten seconds while the group is converging and stop entirely once it isn't. Polling is unfashionable; it is also four lines long and has never woken anyone up.

What we gave up

Honesty demands a list. We lost admission-time validation, so a malformed spec now fails during reconcile instead of at kubectl apply. We lost the generated client, which means a hand-written typed accessor. And we lost the comfort of being able to say "we use the standard framework" in design reviews.

In exchange, the median time to understand a bug went from an afternoon to about twenty minutes, measured across the four incidents we've had since. That trade has been worth making every single time.

If you want to try this

Don't start with a rewrite. Start by writing the three sentences, then instrument the existing controller to see which code runs during a real reconcile. Ours executed about seven percent of its own source. Once you have that number, the argument makes itself — and you can read the rest of my notes on this in the Kubernetes topic.
